# 任务模块开发约束与基础契约

本文件适用于 `tasks/`，同时遵循 [Android 模块约束](../../../../../../../../AGENTS.md)。需求以 [spec.md](../../../../../../../../../spec.md) 为准。

本目录覆盖 R04–R06、R14、R16–R19、R31、R33–R34。请求契约已接入同一应用状态数据库的持久队列、提交／观察、单任务协调器与阶段控制／恢复。已注册各后端通用的书库同步、个人 OneDrive 目录浏览、单格式副本／已下载版本检查、按需封面及已读写回处理器；提交及控制后通过 `QueueWorker` 驱动应用容器共享的 `TaskCoordinator.drain()`；任务页查询持久状态并请求后台唤醒。协议 fixture 与真实 SQLite 证据见 [第二阶段记录](../../../../../../../../verification/phase-2.md)。

## 提交对象与去重

[TaskRequests.kt](api/TaskRequests.kt) 提供书库同步与目录浏览（候选请求）、单格式复制／下载与版本检查、可见页封面批次及已读写回请求。格式资源使用完整书籍身份、格式与后端定位，可附带源版本比较前提。`FrozenSet` 在构造时复制并去重，内容不随调用方修改，集合顺序不影响等价性；批量下载按单格式请求拆分，封面批次的书籍集合在提交时确定，都不能重新查询并扩大提交集合。

`RequestKey` 包含完整请求及必要依赖，包含定位与版本比较前提，不包含触发来源。只可复用等价的未完成请求；用户主动请求等价自动任务时，持久队列负责复用并提升，而非重复传输。提交事务校验依赖属于同一书库；新节点只指向已有节点，且不提供依赖修改接口，因此不能建立自依赖或循环。`SUCCESS` 等待前置任务成功完成，`FINISHED` 只等待前置任务以任何结果结束。

已读写回 `ReadStatusWrite(libraryId, column, batch)` 不经 `submit` 提交（会被拒绝），只经 `DurableTaskQueue.submitReadStatus`／`TaskCoordinator.submitReadStatus`，见下文“已读写回任务”。

## 优先级与调度边界

[TaskContracts.kt](api/TaskContracts.kt) 保存不透明 task ID、书库身份、原始来源、当前优先级、同级排队序号、依赖、阶段、静态进度、结果与阶段控制能力。书库身份沿用每个有效书库代次独立的 `LibraryId`，不按源数字 ID 匹配任务。enum 具有显式持久化字符串 code，不能保存 ordinal；封闭类型的序列化使用 [TaskCodec](persistence/TaskCodec.kt) 的版本与显式标签；schema v2 通过非破坏迁移加入任务和依赖表。

用户下载、为打开而下载、手动同步、已读／未读写回为高优先级；可见封面、启动同步、已下载格式更新为低优先级。必要前置请求及后续阶段沿用父请求来源和优先级，不按操作类型自行降级。自动任务提升保留原始来源，并保存此次用户来源和新分配的高优先级序号；必要前置任务也必须提升。序号由持久队列事务分配，不能由时钟或 WorkManager 的启动顺序代替。

`compareSchedulingPositions` 只比较优先级和同级序号，不是调度器。调度先筛选当前激活书库、网络／授权条件、依赖满足且未暂停的任务，等待项不阻塞无关可执行任务；同一时间只执行一个任务；执行中的低优先级任务在可暂停阶段的安全边界发现已排队的高优先级请求时让出（R17、Q72），回到队列并保留原序号，用户请求完成后在同一次派发中自动继续。已读写回推送成功后提交的同步由协调器记为下一个任务，可执行时必定紧接执行，不插入其它任务（R16）；推送阶段不可暂停、取消或让出。

## 已读写回任务

R13–R16 的已读写回只使用以下机制（Q75–Q81）；不保存提交证据、写前备份或恢复记录，也没有写后刷新阶段。

- **变更列表**：任务请求只含书库、栏目身份与使 `RequestKey` 永不相等的 `batch`；书籍 → 明确目标值保存在 `read_status_changes`。`submitReadStatus` 在一个事务内把点击并入同书库、同栏目、尚未开始（`queued_tasks.started = 0`）的未结束写回，同一本书以最后一次为准，返回 `Reused`；否则新建任务（`Created`），对同书库其它未结束写回各加一条 `FINISHED` 依赖，因此按提交顺序执行。协调器选中任务的事务置 `started = 1`，与合并事务互斥：点击要么在任务开始前并入，要么进入新任务，执行中的变更列表固定。同一事务还从同书库、同栏目已失败或取消的写回中删除这些书籍的行，新点击取代旧意图，旧任务重试不会写回旧目标。
- **执行与重试**：阶段 `WRITE_SNAPSHOT` → `WRITE_PREPARE` → `WRITE_COMMIT`。无需修改时可在 `WRITE_PREPARE` 完成。推送被拒（`VERSION_CONFLICT`）、网络失败或结果不明返回 `StageOutcome.Retry`，与其它瞬时错误共用最多 3 次的计数，计数按整轮累计、阶段推进不清零；版本冲突不退避，立即重新排队并在本次派发中继续。处理器的 `recover()` 须回到 `WRITE_SNAPSHOT`，每轮重新取得最新数据库，不复用上一轮暂存。用尽后失败，手动重试重置计数。
- **紧接同步**：处理器在推送成功（或无需推送）后提交普通的书库同步，返回 `StageOutcome.Complete(followUp = syncId)`。协调器在完成事务中把它记入任务的 `follow_up_id` 及 `dispatch_next`；下一次选择时它可执行则必选，否则清除记录、按常规调度，等待条件的同步不阻塞其它任务。
- **待写入状态**：`pendingReadStatus(library, column)` 一次查询返回当前栏目待写入的书籍，每本书取序号最新的一行：未结束写回中为 `Pending`；已完成写回在其紧接同步结束（任何结果）前为 `Pending`；失败、取消或作为单书失效为 `Failed`（取消时 `error` 为 null）。成功同步（含未变化确认）的事务调用 `dismissReadFailures` 隐藏该书库已结束写回的失败，行仍保留供重试；重试清除隐藏标记，再次标记以更新的行覆盖。该映射只供界面在展示层叠加及按钮判定，不进入 `LibraryIndex` 的筛选、搜索与排序。
- 变更行随任务删除：已结束任务保留规则删除任务时一并删除，清理撤销（`revoke`）任务时同时删除。
- **提交入口**：[ReadStatusService](readstatus/ReadStatusService.kt) 从当前导入冻结书籍、取当前有效的已读栏目，复核页面选择代号，源的 `writeCapability` 不可用时拒绝且不建任务；所有书使用同一个明确目标值。
- **处理器**：[ReadStatusWriteTaskHandler](readstatus/ReadStatusWriteTaskHandler.kt) 的 `WRITE_SNAPSHOT` 先调用源的 `finishPendingPush` 收尾，再 `acquireSnapshot(unchangedVersion = null)` 并把快照移入私有 `write-staging/<task>/`，checkpoint 记录本轮代次与基底版本；`WRITE_PREPARE` 核对任务栏目仍是书库偏好中的已读栏目（切换栏目即 `InvalidColumn` 失败，书库 UUID 也取自偏好，因而清元数据后仍可执行），调用 `ReadStatusStaging`，逐书失效记入 `CompletedWithBookFailures`；`WRITE_COMMIT` 以基底版本为前提调用 `pushDatabase`。准备结果只在同一轮的阶段之间保存在内存：任何恢复都回到 `WRITE_SNAPSHOT` 并删除本轮文件，只保留源的推送日志 `push.json`（`PushJournal`，fsync 后原子替换）；日志存在期间同时保留 `*.staged.db`，供源收尾时辨认自己未写完的临时文件，日志清除后随下一次丢弃删除。该目录按任务 ID 随保留规则与清理撤销删除。

`CompletedWithBookFailures` 保留逐书失效原因，失效书籍须属于任务书库；整体失败使用结构化存储原因、栏目失效或书籍身份变化，不保存异常全文、令牌或 URL。取消从不发生在推送阶段，因此已取消的写回没有推送。其他阶段的暂停、取消、继续和重试能力由实际处理器提供。未知进度总量用文字呈现，状态事件与有效缓存发布事件分别表达。

## 启动与实现状态

[StartupSync](background/StartupSync.kt) 使用状态库默认关闭的全局设置和进程守卫。每个进程首次由用户打开主界面且已有稳定目录配置时，开启才提交一次低优先级同步；首次打开没有配置或开关关闭也消耗该进程机会。用户打开信号交给应用进程 scope，Activity 重建不能取消提交与唤醒；后台恢复启动、返回阅读器和普通前后台切换不触发新同步。手动同步与启动同步使用相同候选请求，按原有去重规则复用并提升。没有周期请求或假成功事件。`DurableTaskQueue` 实现提交与观察，`SubmissionResult` 区分新建、复用、提升与拒绝。未注册处理器的功能不能通过协调器提交，当前应用容器注册通用书库同步、OneDrive 目录浏览、完整副本／版本检查、按需封面及已读写回处理器；不创建假源访问或假完成入口。

AC05 的持久调度、并发唤醒、控制、有限重试／退避及阶段恢复采用接口／平台测试；真实退后台、进程中断、设备重启、通知和生产源访问须按步骤 09 获取真机证据，实际完成范围以验证记录为准，不能用协议测试关闭这些验收。

## 平台唤醒与任务页

[BackgroundTasks](background/BackgroundTasks.kt) 只安排不含源数据的一次性唤醒，`QueueWorker` 使用应用容器唯一的 repository 与执行锁恢复和派发。普通唤醒以 `APPEND_OR_REPLACE` 保存后继，覆盖新请求提交与旧 worker 结束的竞态；唤醒链中已有尚未开始（ENQUEUED／BLOCKED）的 worker 时不再追加，它开始后会派发此前已提交的全部请求。PA6 等设备亮屏时无 wake lock 也会挂起 CPU，因此由 [CpuAwake](background/CpuAwake.kt) 按明确状态持有 `PARTIAL_WAKE_LOCK`（只保持 CPU，不影响熄屏）：主界面在前台时，从请求唤醒到 worker 开始执行（之后由平台任务的锁覆盖），离开前台即释放；图书馆页加载页面／提交封面及读取刚完成的封面期间持有，结束（含取消）即释放。不按经验时长设置超时。网络等待和平台失败分别使用独立重试链，普通用户唤醒不能被旧链退避阻塞。条件不足或退避未到期不忙循环，WorkManager 顺序不代替应用排序。源声明需要网络（`LibrarySource.requiresNetwork`，当前为 OneDrive）的离线任务等待网络，其余保持可调度。worker 停止保留持久阶段／暂存，恢复仍调用处理器核验，不把旧 Running 当作活跃执行或成功。

长任务先请求静态 `dataSync` 前台执行通知，再派发源处理器；平台拒绝执行时保留任务并记录平台等待，不能报告源任务完成。通知与系统后台限制在独立页面呈现，不保证忽略权限／省电限制、精确启动或强行停止后的持续运行。平台异常退避与源处理器最多三次瞬时错误重试是不同层次，不能混为无限源重试。

任务页分“进行中”“已完成”标签并按用户请求／自动任务筛选（Q62），分页显示任务类型、置顶箭头标示的用户请求（含提升）、排队序号或等待原因、阶段进度及实际阶段控制，自动封面批次折叠为一行（Q73）；进度变化默认最多每两秒显示一次，状态变化可即时显示。界面不推算未知总量，不添加滚动、加载／过渡动画，动态值通过资源参数呈现。

## 任务测试与验收设计

遵循 Android 模块的分层验收规则。网络／授权失败、流中断、版本变化以及暂停、取消、重试和恢复的组合，优先通过后端或处理器接口作确定性故障注入；涉及恢复证据、队列事务和文件发布时使用真实平台 SQLite 与私有文件。断点验收须证明已确认的非零偏移、恢复分支及最终字节一致，不能只凭任务最终成功宣称续传。

真实后端集成以最小必要路径补足接口测试，测试侧可包装真实源流控制中断，执行使用应用容器共享 repository 与执行锁；不为测试另建绕过生产调度边界的并行执行器。已有有效证据且未受本次改动影响的故障组合不要求在每轮人工验收重复计时、断网或改源。真实进程强停／重建、系统后台调度、通知和外部阅读器授权仍须在相应阶段用真实设备验证；重新构造处理器或注入恢复记录仅证明协议恢复，不能记作真实进程终止或系统后台验收。

## 源访问边界

生产任务处理器通过存储后端访问源，不将源客户端或任意路径暴露给提交方。错误、事件和日志不得携带凭据或原始响应。

## 执行与恢复协议

- [DurableTaskQueue](persistence/DurableTaskQueue.kt) 的事务分配序号并保存请求、来源、提升、依赖、阶段、结果、重试期限及私有暂存代次／源版本。所有协调器必须使用应用容器共享的同一个 repository 与执行锁；不能在 Activity 或 worker 中另建执行器状态。条件函数只读取已知状态，不在选择事务中隐式访问源。
- [TaskCoordinator](persistence/TaskCoordinator.kt) 连续执行一个资源的阶段；完成、等待、失败、用户安全暂停或让出后才重新选择资源。可暂停阶段运行期间，`checkControl()` 还检查是否有已排队的高优先级请求：仅在有新提交或控制后才重读队列，所以每块调用的开销仍只是一行查询。让出与暂停相同地保留暂存，任务回到“排队”并标记需要恢复，继续前由处理器 `recover()` 核验；让出不调用 `stopped()`。高优先级请求因外部条件不能执行时，会在下次选择中转为等待，低优先级任务只为它让出一次。处理器须在支持控制的阶段循环中调用 `checkControl()`（按主键只读该任务的 `revoked`／`control` 两列，可在每个读缓冲块调用），收到控制异常后关闭句柄并停止工作；不能忽略控制后继续发布。阶段控制由实际处理器提供，不承诺任意阶段可中断。
- 已读写回的恢复、重试与紧接同步见“已读写回任务”。切换书库停放旧库任务，不能阻塞新库的独立工作。
- 恢复、继续及重试都先调用处理器 `recover()` 重新核验源版本与暂存。队列不会仅凭 Running 或曾存在暂存判成功。瞬时网络错误与服务端限流／暂时错误（`THROTTLED`）最多自动重试三次，指数退避与服务端等待取较长者，退避期分别显示等待网络与等待限流；离线等待和永久错误分别处理，下一次唤醒不忙循环。
- 限流按书库生效（R08）：任一后端的 `THROTTLED` 重试时协调器把服务端 Retry-After（缺失时用本任务退避）记入 `source_throttle`，范围为任务所属书库（导入前的候选为其 scope 书库或选择代号），截止前同范围的其它源任务在选择事务中显示等待限流，并以截止时间作为后台唤醒时刻；其它书库不受影响。当前只有 OneDrive 报告限流。截止时间只延长不缩短，进程重启后仍遵守，过期行在选择时删除。
- 按路径找不到源文件且源声明 `resyncsMissingPath`（R11，Q54，当前为 OneDrive）：副本、版本检查与封面处理器经 `staleSource` 提交一次当前书库的元数据同步（应用容器经 `StartupSync.request`），来源与优先级继承该任务的有效来源，并返回 `StageOutcome.AwaitSync`；协调器把找不到的路径记入 `missing_path`，并为同步任务添加一条运行时依赖边（`task_dependencies` 中要求为 `awaited_sync`，同步以任何结果结束即满足；`QueueEntry.sourceSync` 由该边读出），任务等待依赖且不被本轮驱动延后，同步结束后按新导入重新执行一次（副本任务此时允许新路径）。新导入的路径未变时不再请求、直接失败；路径变化后仍找不到也失败；只有同步成功完成才把已下载副本标为源已不可用。每个任务只同步一次，用户重试删除该边及路径记录。不循环，不以列目录搜索文件；其它源直接确认缺失。
- 需要重新登录（OneDrive `LOGIN_REQUIRED`）与本地目录授权撤销（本地 `AUTHORIZATION_EXPIRED`）由源的 `reauthorization` 声明，处理器经 `authorizationWait` 返回等待登录／等待目录授权，保留可复用暂存；OneDrive 403 等永久无权限仍判为失败。成功登录、目录重新授权及每次打开主界面调用 `BackgroundTasks.resumeAuthorizationWaits()`，由 [AuthorizationResume](background/AuthorizationResume.kt) 处理：书库任务随唤醒重新执行；候选任务绑定选择代号与授权，对应后端 `LibraryAuthorization.ready()` 后，仍属当前选择（或重选回同一已导入书库，本地目录重新授权即如此）时以等价新请求继续并取消旧请求，不会因此切换当前书库，已无法执行的旧候选取消。不能取消当前代号的候选，否则会撤销该代号。
- `CandidateConfiguration` 只承接内部注册的配置源访问，使用选择代号、后端和不含凭据的授权会话 ID，不分配 LibraryId，不能带书籍或写回依赖。同步（`LIBRARY_SYNC`）的代号须为当前选择的代号；目录浏览的代号须为进行中添加（`library_addition`）的代号，浏览不改变当前选择，提交时也不记录 `scope_library_id`。两者都须与记录的授权会话一致；重新开始或放弃添加、换账号登录或重选书库都使旧代号失效。取消同步任务在控制事务中撤销当前选择的旧代号，取消浏览任务不影响添加；执行中的旧候选结束不能发出成功缓存事件。真正验证后的发布仍须调用状态库的代号校验事务，禁止先检查再无条件写入当前配置。
- 状态事件在数据库提交后发出；观察者重新读取持久状态。`cachePublished` 只能在实际完整缓存发布之后使用；阶段完成、临时文件生成或源写入确认都不等于缓存发布。生产处理器须遵守后续传输／导入的原子发布契约。

## 书库同步任务

所有后端的书库同步都是同一种候选请求 `CandidateConfiguration.LIBRARY_SYNC`，由 [LibrarySyncTaskHandler](sync/LibrarySyncTaskHandler.kt) 经统一源接口与 `MetadataRepository.sync` 执行；旧版本按后端区分的操作名在解码时映射到它。手动、启动、重新授权后继续和路径失效同步都经 `StartupSync.request` 提交，请求的上下文由后端的 [LibraryAuthorization](api/LibraryAuthorization.kt) 绑定：

- `bind`：为当前选择给出同步上下文；授权已变化时（OneDrive 新登录会话）以新代号换绑当前选择，从而撤销旧授权的请求。本地以选择代号作为不含凭据的授权标识，重新授权即重新选择目录。
- `check`：授权已不是请求绑定的那一个时抛出可分类的源失败，处理器据源的 `reauthorization` 等待登录／目录授权。
- `within`：在请求的授权下访问源（OneDrive 绑定会话，并把网络／服务端原因的刷新失败归为网络失败）。
- `ready`：该后端的等待授权任务现在能否继续。

处理器在复制块边界及发布前检查控制、选择代号与授权；选择已被替换的请求失败且无任何发布，暂停／取消清理本次暂存。恢复重新获取源并检查版本、日志与私有 SQLite 完整性。成功须经统一元数据导入器完整验证并在状态库事务中发布身份／代次，之后才发 `CacheChanged`；快照按任务与不可变尝试代次隔离。取消会撤销选择代号，再次验证必须取得新的当前代号。各后端的实现在 `local/`、`onedrive/`，只在应用容器的 `libraryAuthorizations` 注册。

[MetadataViewModel](../ui/MetadataViewModel.kt) 与图书馆页的同步状态只读取本地配置和持久队列（`latestLibrarySync`）；显式同步／继续／重试请求共享后台执行。启动自动同步由进程启动门独立提交，页面恢复不能重复创建。

## OneDrive 选择书库根

[OneDriveCandidateTaskHandler](onedrive/OneDriveCandidateTaskHandler.kt) 只做本人 drive 发现与完整目录加载（选择书库根，按设计绑定 OneDrive）；选中根后的同步是上面的通用书库同步，不再请求 drive 发现，账号由后端本地核对，上次导入的 cTag 交给源，未变化时只更新同步时间（Q55）。候选请求保存目录 item ID，不保存 nextLink；旧请求页码仅为持久格式兼容保留，执行／恢复均从第一页重新取完服务器分页。每个服务器页边界检查任务控制，完整结果按 task ID 原子保存；仅在进行中添加的代号与授权会话仍匹配且任务成功时可读，缺少完整标志的旧分页结果不可用于本地翻页。目录结果不能绑定书库身份；选择根只经状态库比较添加代号的事务写入添加记录，完成添加时才加入书库列表并成为当前选择。等待登录的浏览只在仍属于进行中添加时由 `AuthorizationResume` 在新会话下继续，否则取消。

[OneDriveCandidateService](onedrive/OneDriveCandidateService.kt) 只负责显式提交、根选择和私有恢复查询；恢复不联网。重新登录产生新的授权会话，旧任务不得复用令牌访问新账号。添加向导第 2 步的目录选择不改变当前书库，进入目录显式提交完整加载任务，本地分页只切换已加载列表，不访问 Graph、不提交任务；这些操作不激活书库；只有点击选择当前目录才保存稳定根位置。页面导航取消不选择新目录。已选位置在重新登录后同步时由 `OneDriveLibraryAuthorization.bind` 换绑到新会话，并由后端核对实际账号。浏览处理器没有上传、源删除或书籍副本发布；书籍发布由独立副本处理器负责。

## 完整元数据导入

书库同步调用 `MetadataRepository`，只有结构解析、完整索引与快照原子发布成功才完成并发出缓存事件；目录浏览不会发出缓存事件。发布事务同时记录任务完成，完成后不再接受暂停／取消；事务复核选择代号与任务暂停／取消标记，过期结果不能激活新配置。恢复重新取得源快照及完整导入，不凭旧阶段或暂存文件宣称成功。当前候选同步的源访问与导入在同一可恢复执行阶段完成，支持块边界控制；任务页只呈现实际持久阶段与处理器已报告进度，未知总量使用文字。

## 完整书籍副本

- `copies/CopyService` 从当前导入冻结完整书籍／格式键与逻辑路径，提交时复核页面选择代号；提交方不解析源文件。`SourceFileLocator.Relative` 保存经过模型校验的逻辑路径，执行后端仍负责授权根解析。用户请求同资源自动更新时复用其版本前提并提升优先级。
- `FormatCheck` 是独立单格式源检查任务，随导入在同一事务按已有清单及源的 `checksCopy` 入队（OneDrive 只入队 Calibre 记录有变化的副本，见[元数据约束](../metadata/AGENTS.md)）；只在已下载记录仍存在且源版本改变时提交 `FormatCopy`，版本未变时补记当前导入的 Calibre 记录。明确书籍身份／格式缺失或源文件缺失才更新不可用状态；网络／登录／权限失败保持既有确认状态。
- `copies/FormatCopyTaskHandler` 每次传输只经 `LibrarySource.lookup` 观察源一次，取得版本、长度、可选内容散列与流；发布前询问 `unchanged`，本地重新核对版本，OneDrive 信任该次观察（R08 允许同步间隔内过期）。源提供内容散列（本地 SHA-256 版本）时须与传输字节一致。处理器在后台逐块检查任务控制、书库身份与空间。完整本地 SHA-256 与传输字节一致，OneDrive 使用 cTag、可知长度及传输流完整结束；本地 SAF 文档大小（缺失时为导入元数据大小）只作进度总量与下载前空间预检，不参与完整性判断；EPUB 全条目 CRC 与必需入口、PDF 头尾再作格式校验，这些是传输完整性检查，不是阅读器渲染验证。
- 暂存与恢复证据位于 `book-staging`，部分文件先 fsync 再原子保存绑定源版本的 offset／SHA-256 私有证据；暂停及可重试中断保留已确认前缀，恢复校验散列并截断未确认尾部。同版本通过本地 SAF 直接 seek 或 OneDrive 严格校验的 Range 接续；不支持范围访问、版本变化或断点损坏时重新传输，固定版本前提冲突则拒绝。完整验证后的恢复直接进入发布阶段。未验证内容不进入 books；取消在安全边界清理暂存，旧完整副本保留。处理器 `stopped()` 由共享协调器在控制边界调用；已取消且有 checkpoint 的任务在下一次 drain 回收暂存。
- 发布时同步完整文件及相关目录，再在状态库事务核对当前书库、任务控制及 revoked 标记，发布清单与完成状态。只在成功事务之后发缓存事件；新代次不原地覆盖旧文件。普通查询／打开与代次回收共享读取门，已打开句柄直到关闭继续使用旧代次。精确范围清理与后台执行共享同一队列边界。

- 任务队列页显示时调用 `TaskCoordinator.restorePending()`：仅在共享执行锁空闲时恢复私有 Running 记录为可显式执行的排队状态，不等待运行中的处理器、不探测源、不自动传输。正在执行的任务保持原状态；不能把旧 Running 记录当成当前活跃执行。

## 按需封面处理器

`CoverService` 把当前页缺失的封面作为一个批次提交（R10、Q73），只接受已导入、属于当前选择的完整 BookKey，复用对象集合相同的未完成批次，并结束该书库其它尚未开始的自动封面批次；正在执行的旧批次由 `CoverTaskHandler` 经 `newerCoverBatch` 发现后不再开始新的封面，已开始的完成后以取消结束。处理器在 `COVER_TRANSFER` 阶段按 `LibrarySource.parallelReads`（本地 3、OneDrive 2）同时读取、缩放并发布封面，每个进行中的封面使用批次暂存下自己的子目录；任一封面抛出控制、让出或批次级源错误时，结构化并发取消其余封面并清理暂存，已有缓存的跳过（续跑不重做），单个封面缺失或损坏记入 `CompletedWithBookFailures`，导入变化、授权或网络问题结束或挂起整个批次；按页进度写入 `TaskProgress`。`COVER_PUBLISH` 只为旧版本持久化的单封面任务保留，恢复时从传输阶段重来。原图版本与缩略图／图片流由 `LibrarySource.openCover` 一次取得（OneDrive 一个请求），发布前不再重读源；路径固定为该书籍导入目录的 `cover.jpg`，没有书籍格式内容读取。控制边界、尺寸限制及原子发布见[封面缓存约束](../storage/covers/AGENTS.md)。元数据导入不创建整库封面任务；返回某页时只为仍缺失的封面重新提交批次。后台驱动使用同一共享协调器。

## 已结束任务的保留

已结束任务（完成、失败、取消）只保留调度序号最新的 `DurableTaskQueue.FINISHED_HISTORY`（50）条（R18、Q74）。`CacheMaintenance.recoverLocked` 在每次 `restorePending()`／`drain()` 前、没有其它清理 journal 时调用 `pruneFinished`：同一事务删除更早的任务行及其出边，并写入 `INPUTS` journal 列出这些任务的 `book-staging`、`cover-staging`、`snapshots`、`write-staging`、`onedrive-browser` 私有文件，随后按 journal 删除，进程中断后下次恢复继续。以下任务不删除：

- 其 `TaskOwner` 仍持有：每种 `TaskRequest` 必须声明 `owner`，由编译器保证不会遗漏。`TaskOwner.Queue` 表示队列外无人持有；`TaskOwner.Selection` 表示创建它的选择（及可选的进行中添加）仍为当前时由其持有，例如向导按任务 ID 读取的目录结果。新增需要在队列外按任务 ID 读取结果的任务类型时，为它声明对应的 owner，而不是在清理处添加特例。
- 仍是 `task_dependencies` 中任一边的前置任务，包括提交时的依赖和运行时添加的路径失效同步。任务之间的新引用一律使用依赖边，清理无需改动。
- 自身还保留 checkpoint（待 `stopped()` 回收）。

## 清理撤销与恢复

缓存清理与任务发布共享状态事务及 `executionLock`。清理事务永久设置匹配任务的 `revoked`，控制／重试和发布均拒绝这些旧任务；执行中的处理器经 `checkControl()` 在安全边界停止，清理等待执行锁后删除对应暂存。存在 `cache_cleanup` journal 时拒绝新提交及派发，`beforeDispatch` 在 `restorePending()`／`drain()` 内先恢复私有清理，再恢复一般任务，不发起源访问。清理失败保留 journal；恢复不能依赖当时的当前书库或源授权。

格式移除匹配冻结 BookKey／格式的 `FormatCopy` 和 `FormatCheck`，范围外格式、任务及 checkpoint 保持。清元数据匹配当前库快照候选和封面，保留已读写回（它自己取得最新源数据库，R12）。其它库清理与删除书库撤销该书库的全部任务，包括已读写回，并删除其变更行。

候选任务除 request 自带身份外使用 `scope_library_id`；新候选提交记录已知当前身份，完整导入成功时记录实际激活身份。v5 迁移仅按当前选择代号、已知位置或可无歧义匹配的私有快照补归属；无法证实的旧候选不按名称猜测，不能将已知 scope 的覆盖宣称为所有历史候选均已覆盖。清理匹配及路径范围以[CacheMaintenance](../storage/cache/CacheMaintenance.kt)为准。

对于无法重建所属书库、代号既非当前选择也非进行中添加的旧候选输入（如已放弃添加的浏览），恢复阶段通过同一持久清理日志回收该任务的快照／浏览暂存。删除书库（`CleanupKind.LIBRARY`）按其它库清理的范围撤销该位置所有绑定的任务，删除当前书库时还撤销当前选择代号下的候选任务。此类请求不能再次激活；不猜测所属书库，也不触及完整导入、书籍或保护域。
